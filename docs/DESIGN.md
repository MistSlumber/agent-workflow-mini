# 设计取舍

## 为什么是线性循环，不是图

LangGraph 一类框架用节点和边显式描述流转，适合分支多、需要人工介入、长任务暂存的流程。但本仓库要讲清的是「循环在哪里失控」，线性 `while not state.done` 加上五个检查点，比图更容易逐行验证。等分支真的多起来，再迁移到图不迟。

## 为什么策略不能改状态

`Policy.decide(state, available)` 只返回工具名和参数。如果允许策略直接写 `state.done = True` 或改 `step`，最大步数和终止条件就形同虚设——这对确定性规则没什么，对 LLM 策略是真实风险。所有状态变更集中在 `Agent.run()` 里。

## 为什么工具异常不中断流程

工具失败是常态：网络超时、订单不存在、参数格式不对。把异常记进 `trace` 和 `context["last_error"]`，再交给下一步决策（示例中自动 `escalate`），比直接抛到最外层更符合真实业务。代价是要防止「一直失败一直重试」，这由 `max_steps` 兜底。

## 为什么检查点每步都写

演示规模下每步写一次 JSON 很便宜。真实系统里可以改成异步或按关键步骤写，但「状态可序列化」这件事必须从第一天就设计好，否则后面加中断续跑要重构整个状态模型。

## 超时的边界

`wall_timeout` 是**总时长预算**，在每步开始前检查，不是单个工具的强制超时。同步函数无法在 Windows 上可靠地被外部中断；如果某个工具可能长期阻塞，应在工具内部用超时客户端，或改成线程池 + future.result(timeout)。这里刻意不引入线程，保持可读；示例中通过可注入的 `clock` 让超时逻辑可测。

## 三条明确不做

- 不实现 MCP 协议或远程工具发现；
- 不实现多智能体协作与消息总线；
- 不内置任何向量库、模型客户端或 Web 框架。

这三条都不是当前要解决的问题。
